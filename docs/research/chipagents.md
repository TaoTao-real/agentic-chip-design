# ChipAgents：让工程工具提供可查询的观测

核对日期：2026-09-24。阅读范围：厂商公开的 RCA 和 timing closure 文章。没有访问产品内部实现、客户环境或独立复现数据；以下厂商机制描述不等于第三方验证。

## 公开资料支持的方向

RCA 文章介绍面向 Agent 的 waveform 查询与分析机制，而不是要求模型一次读取整个波形；其中也涉及专门模型训练和 prover/verifier 组织。timing closure 文章强调快速内部反馈与可信工程工具确认相结合。[S1][S2]

这支持“重新设计工具如何提供信息”的研究方向，但不能据此证明同一未经适配的模型只加 JSON 摘要就能取得相同效果，也不能把厂商示例数字直接搬成本项目收益。

## 对本项目的分析

最值得学习的是将原始产物变成可查询的工程对象。我们的第一段先确定性提取当前候选路径、失败、版本和约束，再按需查询设计片段；主 Agent 集中做假设与变换，不重复恢复全部上下文。

快速 PPA 反馈仅作为排序或晋级证据，最终接受仍由冻结的独立工具决定。相关性低的近似指标不能被包装成 ground truth，特别是在综合与布线排名改变时。

## 差异化应如何表达

不能说“他们会读报告，我们不用读报告，所以一定更先进”，也不能根据公开资料没有提到某种 IR 就断言其内部不存在。

我们可检验的假设是：PyCircuit 在构建设计时原生产生来源与契约，使同一 Agent 少做逆向恢复；ChipContext 负责可追溯的当前证据；规范化实验分离这些机制的增量。价值来自效果和维护成本，而不是另起一套多 Agent 命名。

## 最小对照与采用顺序

先比较专家 Prompt+原始查询、自写脚本，与确定性结构化反馈。必要时再比较专用查询索引、辅助判断模型和并行假设；分别统计重复读取、错定位、无效候选、token、P&R 与端到端成本。

v1 先保持一个主 Design Agent；短生命周期并行探索可后加，但复制完整仓库上下文和无限子 Agent 不是节约 token 的默认方法。全部辅助成本必须归入实验。
